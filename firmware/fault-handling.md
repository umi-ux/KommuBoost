# Fault Handling

## Two-bucket recovery policy

Faults are classified into two buckets, each with different recovery behavior:

| Bucket | Recovery behavior |
|---|---|
| Transient / environmental | Auto-recovers once the condition clears |
| Compute-integrity | One retry allowed per drive cycle. If the fault recurs within the same drive cycle, escalates to requiring an ignition cycle before further retry is allowed |

### Why this split is safety-justified

Under ISO 26262, once a safe state is reached instantly (satisfying the Fault Tolerant Time Interval), how quickly the system recovers becomes an availability question, not a safety question. The safe state (pass-through) is already guaranteed the moment a fault is detected; recovery timing affects uptime, not safety.

The two-bucket policy is justified against the ASIL B latent fault detection metric (60% or greater), not against prescriptive text in the standard. In a safety review, the answer is "this meets the latent fault metric," not "this is standard practice."

## `fault_classify()`

This function assigns each detected fault to a bucket.

| Fault code | Meaning | Bucket | Status |
|---|---|---|---|
| `CAN_TIMEOUT` | No fresh CAN message from KommuAssist2 | Transient | Confirmed |
| `LINK_TIMEOUT` | Main MCU to supervisor UART link went stale | Transient | Confirmed |
| `HEARTBEAT_LOST` | Supervisor stopped seeing the main MCU's heartbeat pulse | Compute-integrity | Confirmed |
| `WATCHDOG_RESET` | Chip came back up via an IWDG-triggered reset | Compute-integrity | Confirmed |
| `OUTPUT_MISMATCH` | LM393 comparator flags the output voltage as wrong | Compute-integrity | Confirmed |
| `SELFTEST_FAILED` | Startup self-test failed | Compute-integrity (default) | Pending FMEDA review |
| `SIGNAL_MISMATCH` | MAIN and SUB readings don't correlate as expected | Compute-integrity (default) | Pending FMEDA review |
| `OUT_OF_RANGE` | A sensor reading is outside the valid voltage window | Compute-integrity (default) | Pending FMEDA review |
| `SIGNAL_STUCK` | A sensor reading hasn't changed for longer than expected | Compute-integrity (default) | Pending FMEDA review |
| `POWER_RAIL` | The board's own power rail reads out of range | Compute-integrity (default) | Pending FMEDA review |
| `DRIVER_OVERRIDE` | Driver torque input overpowers the assist | Compute-integrity (default) | Pending FMEDA review, see note below |
| `SUPERVISOR_DENIED` | Supervisor withheld approval without a more specific reason | Compute-integrity (default) | Pending FMEDA review |

5 of 12 are confirmed. The remaining 7 are placed in the compute-integrity bucket as a conservative default, not as a reviewed decision, and should not be treated as final.

`DRIVER_OVERRIDE` is worth flagging specifically: driver override is normal driving behavior, not a malfunction. Left in the current strict default, a driver overriding assist a few times in one ordinary drive could force an unnecessary ignition-cycle-required lockout. This is the strongest candidate for reclassification in the pending review.

## `FAULT_OUT`

`FAULT_OUT` is a hardware signal from the LM393 comparator on the board, read by firmware as an input and never generated by firmware. Fault logic referencing `FAULT_OUT` treats it as ground truth from hardware.

## Watchdog-reset detection

Both chips check, on every boot, whether they just came back from an IWDG (watchdog) timeout, meaning the previous cycle hung and the hardware watchdog force-reset the chip. If so, `FAULT_WATCHDOG_RESET` is reported once. On the main MCU this routes through the normal two-bucket recovery policy; on the supervisor, which has no fault-recovery state machine, it is a one-time diagnostic report rather than something that blocks the gate beyond that cycle's live checks.

## Remaining fault-coverage gaps

- **Supervisor power rail self-check.** No ADC channel or pin exists for this in the current pinout. See [Supervisor MCU](supervisor-mcu.md).
- **Recovery-latch enforcement is main-MCU-only.** The supervisor has no fault-recovery state machine by design (continuously re-evaluated each cycle). Whether it should adopt some form of fault memory is a deliberate design question, addressed in [Supervisor MCU](supervisor-mcu.md).
- **UART checksum strength.** A simple additive byte sum, which will not catch certain corruption patterns such as two swapped bytes with the same sum. Upgrading to a CRC is recommended before a production revision.

## Debounce and escalation logic

Two issues were identified and corrected in the fault-handling logic on both chips:

1. **Debounce counter scoped per fault type.** The streak now resets whenever the fault type changes between cycles, so a rail glitch, a range glitch, and a correlation glitch across three consecutive cycles are not mistaken for one problem persisting.
2. **Escalation tracked per fault type across the whole drive.** A per-fault-type bitmask (`compute_fault_seen_mask`) replaces a single "last fault" memory, so any fault type recurring within the same drive is caught regardless of what other faults occurred in between.

Both were found through line-by-line review against the intended policy, the standing practice for all fault-handling logic in this project. See [Key Learnings](../key-learnings/README.md).
