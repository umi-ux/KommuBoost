# Fault Handling

## Two-bucket recovery policy

Faults are classified into two buckets, each with different recovery behavior:

| Bucket | Recovery behavior |
|---|---|
| Transient / environmental | Auto-recovers once the condition clears |
| Compute-integrity | One retry allowed per drive cycle. If the fault recurs within the same drive cycle, escalates to requiring an ignition cycle before further retry is allowed |

### Why this split is safety-justified, not just convenient

Under ISO 26262, once a safe state is reached instantly (satisfying FTTI — Fault Tolerant Time Interval), *how quickly the system recovers* becomes an **availability** question, not a safety question. The safe state (pass-through) is already guaranteed the moment a fault is detected — recovery timing doesn't compromise safety, it only affects uptime.

The two-bucket policy itself is justified against the **ASIL B latent fault detection metric (≥60%)** — not against prescriptive text in the standard. This distinction matters if this policy is ever questioned in a safety review: the answer is "this meets the latent fault metric," not "this is standard practice."

## `fault_classify()` — status

This is the function that assigns each detected fault to a bucket. **3 of 10 entries are confirmed; 7 are pending Ting's FMEDA review**, including:

- `SELFTEST_FAILED`
- `SIGNAL_MISMATCH`
- `POWER_RAIL`
- `DRIVER_OVERRIDE`
- (and others — currently placed conservatively pending review)

⚠️ Do not treat the current placement of these 7 as final. They were placed conservatively (i.e. erring toward the more restrictive bucket) as a placeholder, not as a reviewed decision.

## `FAULT_OUT`

`FAULT_OUT` is a **hardware** signal from the LM393 comparator on the board — it is read by firmware as an input, not generated by firmware. Any fault logic referencing `FAULT_OUT` should treat it as ground truth from hardware, not as something to be second-guessed or overridden by software.

## Known gaps in fault coverage

- **`SUB_ADC` stuck-check is not implemented.** Only `MAIN_ADC` is currently watched for stuck values. This is an identified gap, not a deliberate omission.
- **Supervisor power rail self-check is missing.** The supervisor currently has no self-check on its own power rail — an architectural gap identified but not yet closed.
- **Recovery-latch enforcement is main-MCU-only.** The retry/escalation logic for the two-bucket policy is currently only implemented on the main MCU. The supervisor does not yet independently enforce the same latch behavior — see [Open Items](../open-items/README.md#supervisor-side-recovery-latch-enforcement).

## Debounce and escalation — lessons from generated code review

Two real bugs were caught in previously generated fault-handling code before being trusted:

1. A **shared debounce counter** was mixing unrelated fault types together — meaning debounce state for one fault type could be corrupted by an unrelated fault's activity.
2. The **escalation logic forgot earlier compute-integrity faults within the same drive cycle** — meaning the "one retry per drive cycle, escalate on recurrence" rule could be silently bypassed if the fault history wasn't tracked correctly across the whole drive cycle.

Both were caught by deliberate skeptical review, not by test failures. This is the standing justification for reviewing all generated fault-handling logic line-by-line against the intended policy before trusting it — see [Key Learnings](../key-learnings/README.md#generated-code-requires-skeptical-review).
