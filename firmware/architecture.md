## Three-target structure

| Target | Files | Purpose |
|---|---|---|

## Core architectural decisions

- **CubeMX-generated STM32 HAL.** Peripheral init is generated for the exact chip variant, which removes hand-transcription error at the register level.
- **Split-pin gate control: each chip drives its own gate signal, independently.**
  - Main MCU drives `MCU_GATE_ENABLE` from its own boost decision.
  - Supervisor drives `SUPERVISOR_GATE_ENABLE` from its own independent checks.
  - Both feed an AND gate; boost only reaches the output stage if both chips independently agree.
  - This protects against a software bug on either chip alone, since a bug would need to exist on both chips simultaneously to slip through. See [Key Learnings](../key-learnings/README.md).
- **Each chip runs its own fixed-period loop** (`HAL_GetTick()`-driven, ~10ms), so every debounce and timeout constant corresponds to a known, predictable amount of real time.
- **Boost is gated on `STEER_REQ`, then `STEER_CMD`.** See [State Machine](state-machine.md) for the CAN signal detail.
- **Two-bucket fault recovery policy** (main MCU, see [Fault Handling](fault-handling.md)):
  - Transient/environmental faults auto-recover once the condition clears.
  - Compute-integrity faults get one retry per drive; recurrence within the same drive escalates, requiring an ignition cycle (in practice, a power cycle, see the power caveat below).
- **`FAULT_OUT` is a hardware input**, generated by the LM393 comparator, read by both chips, never asserted by firmware.
- **Watchdog (IWDG) is active on both chips**, refreshed every loop cycle. A hang on either chip triggers an automatic reset, detected and reported as `FAULT_WATCHDOG_RESET` on the next boot.

## Power caveat: the "zero power fail-safe" claim is narrower than it sounds

This needs to be stated precisely, because the informal framing used earlier in this project ("zero power, safe pass-through, no firmware needed") overstates what the hardware actually guarantees.

**What is true:** if the board has power but the MCU crashes, hangs, or has a firmware bug, both gate pins fall to LOW and the analog switch (TS5A23157) returns to its default NC path, raw sensor signal to the EPS. This is a genuine, verified safety property: MCU/firmware failure while the board is powered does not require any correct software behavior to reach a safe state.

**What is not true:** the switch does not maintain a connected pass-through path with zero power. The TS5A23157 datasheet is explicit that its NC behavior is defined "when powered on;" internally, the switch's conduction path is FET-based and requires bias voltage from VCC to conduct in any state, including its default one. With VCC entirely absent, the switch goes to a high-impedance (open) state, not a closed one. This was checked against the TI datasheet and confirmed with TI support documentation directly.

**A natural next question, checked and ruled out:** does a "powered-off protection" variant solve this? The TS5A23159 was investigated specifically for this. Its powered-off protection feature means the switch isolates cleanly (avoids leakage or damage) when unpowered, it does not mean it holds a connection when unpowered. Every chip in this switch family shares the same fundamental limitation for the same underlying reason.

**Alternatives investigated, neither suitable:**
- **Mechanical relay.** A true electromechanical relay can genuinely hold an NC contact with zero power (a real, physical spring-loaded connection). This would solve the problem in principle, but was ruled out for this application: relay footprint is large relative to the board's target size, switching speed is far slower than the analog switch, mechanical contacts wear over the vehicle's service life in a way solid-state switching does not, and coil drive current is a meaningfully larger power draw.
- **Optocoupler.** Does not solve the underlying problem at all, an optocoupler still needs power to transmit a signal (the LED side needs current to turn on), so it shares the same "needs power to pass anything through" limitation as the analog switch. It is also poorly suited to continuous analog voltage fidelity, optocouplers are built for digital on/off signal transfer, not for preserving an analog voltage level accurately.

**Net conclusion, stated plainly:** total loss of board power is not currently covered by any fail-safe mechanism, hardware or firmware. If the board loses power, the analog switch opens, and no signal (not the raw signal, not a boosted one) reaches the EPS. This is a real, unresolved gap, and this document previously implied a stronger guarantee than the hardware actually provides. This is the single item most worth Ting's attention, since it affects what can be honestly claimed in the ASIL B safety case.

## Register-level history

An earlier hand-written register approach (`reg_defs.h`) caught one real bug during development: an invented RCC register (`CRRCR`, not present in this chip's actual register map) was silently shifting the offset of `IOPENR` by 4 bytes. It was caught by cross-checking against the reference manual's real register table before anything was flashed. The project now uses CubeMX-generated HAL code, which sources register-level detail from the chip vendor's own verified data rather than manual transcription. See [Key Learnings](../key-learnings/README.md) for the full account.
