## Core architectural decisions

- **CubeMX-generated STM32 HAL.** Peripheral init is generated for the exact chip variant, which removes hand-transcription error at the register level.
- **Split-pin gate control: each chip drives its own gate signal, independently.**
  - Main MCU drives `MCU_GATE_ENABLE` from its own boost decision.
  - Supervisor drives `SUPERVISOR_GATE_ENABLE` from its own independent checks.
  - Both feed an AND gate; boost only reaches the output stage if both chips independently agree.
  - This protects against a software bug on either chip alone, since a bug would need to exist on both chips simultaneously to slip through. See [Key Learnings](../key-learnings/README.md).
- **Each chip runs its own fixed-period loop** (`HAL_GetTick()`-driven, ~10ms), so every debounce and timeout constant corresponds to a known, predictable amount of real time.
- **Boost is gated on `STEER_REQ`, then `STEER_CMD`.** See [State Machine](state-machine.md) for the CAN signal detail.
- **Two-bucket fault recovery policy** (main MCU, see [Fault Handling](fault-handling.md)):
  - Transient/environmental faults auto-recover once the condition clears.
  - Compute-integrity faults get one retry per drive; recurrence within the same drive escalates, requiring an ignition cycle (in practice, a power cycle, see the power caveat below).
- **`FAULT_OUT` is a hardware input**, generated by the LM393 comparator, read by both chips, never asserted by firmware.
- **Watchdog (IWDG) is active on both chips**, refreshed every loop cycle. A hang on either chip triggers an automatic reset, detected and reported as `FAULT_WATCHDOG_RESET` on the next boot.

## Power caveat: "fail-safe with zero power" covers logic/MCU failure, not physical disconnection

The NC analog switch's pass-through default guarantees pass-through when the switch loses its control signal (MCU crash, firmware bug, brownout, both gate pins low). It does not cover the board losing physical continuity with the signal path (a connector coming loose, a broken trace, physical disconnection). In that failure mode, no signal reaches the ECU at all, which is a different failure category from the fail-safe this design covers. Both chips are powered from the same 5V feed as the torque sensor; losing that feed takes the whole board down together, which is the intended safe outcome, but is a distinct scenario from an MCU crashing while the board stays powered.

## Register-level history

An earlier hand-written register approach (`reg_defs.h`) caught one real bug during development: an invented RCC register (`CRRCR`, not present in this chip's actual register map) was silently shifting the offset of `IOPENR` by 4 bytes. It was caught by cross-checking against the reference manual's real register table before anything was flashed. The project now uses CubeMX-generated HAL code, which sources register-level detail from the chip vendor's own verified data rather than manual transcription. See [Key Learnings](../key-learnings/README.md) for the full account.
